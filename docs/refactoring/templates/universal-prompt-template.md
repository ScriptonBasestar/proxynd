## 사용 가이드

### 1. 프로젝트 타입별 커스터마이징

#### Web API 프로젝트
- **주요 리팩토링 영역**: 엔드포인트, 미들웨어, 데이터 레이어
- **핵심 메트릭**: 응답 시간, 처리량, 에러율
- **특별 고려사항**: API 버전 관리, 하위 호환성

#### Library 프로젝트
- **주요 리팩토링 영역**: 공개 API, 내부 구조, 의존성
- **핵심 메트릭**: API 복잡도, 번들 크기, 의존성 수
- **특별 고려사항**: 시맨틱 버저닝, 브레이킹 체인지

#### CLI Tool 프로젝트
- **주요 리팩토링 영역**: 명령어 구조, 옵션 처리, 출력 포맷
- **핵심 메트릭**: 실행 시간, 메모리 사용량, 명령어 복잡도
- **특별 고려사항**: 사용자 경험, 스크립트 호환성

#### Microservice 프로젝트
- **주요 리팩토링 영역**: 서비스 경계, 통신 패턴, 데이터 일관성
- **핵심 메트릭**: 서비스 간 결합도, 메시지 크기, 레이턴시
- **특별 고려사항**: 분산 트랜잭션, 서비스 디스커버리

### 2. 언어별 고려사항

#### 정적 타입 언어 (Java, C#, Go, Rust 등)
- 타입 시스템 활용한 리팩토링
- 컴파일 타임 검증 활용
- 인터페이스 기반 설계

#### 동적 타입 언어 (Python, JavaScript, Ruby 등)
- 런타임 타입 체크 추가
- 테스트 커버리지 강화
- 타입 힌트/애노테이션 활용

### 3. AI 컨텍스트 최적화 팁

#### 대규모 프로젝트 (100K+ LOC)
- 리팩토링 영역을 작은 단위로 분할
- 각 프롬프트당 2-3개 모듈만 포함
- 단계적 접근 필수

#### 중규모 프로젝트 (10K-100K LOC)
- 관련 모듈을 그룹화하여 처리
- 프롬프트당 5-7개 모듈 가능
- 통합 테스트 중요

#### 소규모 프로젝트 (<10K LOC)
- 전체 프로젝트 한 번에 분석 가능
- 포괄적 리팩토링 계획 수립
- 빠른 반복 가능

## 플레이스홀더 설명

| 플레이스홀더 | 설명 | 예시 |
|------------|------|------|
| `{PROJECT_NAME}` | 프로젝트 이름 | "ProxyND", "E-Commerce API" |
| `{PROJECT_TYPE}` | 프로젝트 타입 | "Web API", "Library" |
| `{PRIMARY_LANGUAGE}` | 주 사용 언어 | "Go", "Python", "Java" |
| `{COMPONENT_DIR_1}` | 주요 컴포넌트 디렉토리 | "handlers/", "services/" |
| `{메트릭_1}` | 측정 가능한 지표 | "중복 코드 비율", "응답 시간" |

## 베스트 프랙티스

1. **구체적이고 측정 가능한 목표 설정**
   - ❌ "코드 품질 개선"
   - ✅ "중복 코드 30% 감소, 테스트 커버리지 80% 달성"

2. **점진적이고 안전한 접근**
   - 한 번에 모든 것을 바꾸지 않기
   - 각 단계마다 검증 포인트 설정
   - 롤백 계획 수립

3. **팀과의 협업 고려**
   - 리팩토링 계획 공유
   - 코드 리뷰 프로세스 활용
   - 지식 공유 세션 계획

4. **자동화 도구 활용**
   - 정적 분석 도구로 문제점 발견
   - 자동 리팩토링 도구 활용
   - CI/CD 파이프라인에 검증 추가
