# 범용 리팩토링 원칙

## 개요
이 문서는 프로젝트 타입, 언어, 프레임워크에 관계없이 적용할 수 있는 범용 리팩토링 원칙을 정의합니다.

## 🎯 핵심 리팩토링 원칙

### 1. 점진적 개선 (Incremental Improvement)

#### 원칙
- **작은 단위로 변경**: 한 번에 하나의 문제만 해결
- **지속적 검증**: 각 변경 후 즉시 테스트
- **되돌리기 가능**: 모든 변경은 쉽게 롤백 가능해야 함

#### 실천 방법
```
1. 변경 범위를 최소화 (하나의 파일/클래스/함수)
2. 기능 동등성 유지 (리팩토링 != 기능 추가)
3. 각 단계마다 커밋 (원자적 변경)
4. 자동화된 테스트로 검증
```

### 2. 기존 동작 보존 (Behavior Preservation)

#### 원칙
- **외부 인터페이스 유지**: API, CLI, UI 변경 최소화
- **기능 동등성**: 리팩토링 전후 동일한 결과
- **성능 저하 방지**: 리팩토링으로 인한 성능 영향 모니터링

#### 검증 체크리스트
- [ ] 기존 테스트 모두 통과
- [ ] 성능 벤치마크 결과 동등 이상
- [ ] 외부 인터페이스 변경 없음
- [ ] 사용자 경험 영향 없음

### 3. 명확한 의도 표현 (Clear Intent)

#### 원칙
- **자기 문서화 코드**: 코드 자체가 의도를 설명
- **명시적 네이밍**: 변수, 함수, 클래스명이 역할 표현
- **단일 책임**: 각 컴포넌트는 하나의 명확한 책임

#### 개선 예시
```
# Before (언어 중립적 의사코드)
function calc(x, y, t) {
    if (t == 1) return x + y
    if (t == 2) return x - y
    if (t == 3) return x * y
    return x / y
}

# After
function calculate(operand1, operand2, operation) {
    switch (operation) {
        case Operation.ADD: return add(operand1, operand2)
        case Operation.SUBTRACT: return subtract(operand1, operand2)
        case Operation.MULTIPLY: return multiply(operand1, operand2)
        case Operation.DIVIDE: return divide(operand1, operand2)
    }
}
```

### 4. 의존성 최소화 (Minimize Dependencies)

#### 원칙
- **느슨한 결합**: 컴포넌트 간 의존성 최소화
- **높은 응집**: 관련 기능은 함께 그룹화
- **의존성 역전**: 추상화에 의존, 구체화에 의존 X

#### 측정 지표
- 순환 의존성 수: 0 목표
- 팬인/팬아웃 비율: 균형 유지
- 결합도 지수: 낮을수록 좋음

### 5. 테스트 가능성 향상 (Improve Testability)

#### 원칙
- **격리 가능한 단위**: 각 컴포넌트 독립적 테스트 가능
- **의존성 주입**: 외부 의존성은 주입 가능하게
- **부작용 최소화**: 순수 함수 선호

#### 리팩토링 패턴
1. **Extract Method**: 긴 메서드를 작은 단위로 분리
2. **Introduce Parameter**: 하드코딩된 값을 매개변수로
3. **Replace Constructor with Factory**: 복잡한 생성 로직 분리
4. **Introduce Seam**: 테스트 가능한 경계 생성

## 📊 리팩토링 우선순위 결정 프레임워크

### 위험도-영향도 매트릭스

```
높은 영향도
    │
    ├─────────────┬─────────────┐
    │      A      │      B      │
    │  (최우선)   │   (높음)    │
    ├─────────────┼─────────────┤
    │      C      │      D      │
    │   (중간)    │   (낮음)    │
    └─────────────┴─────────────┘
                            낮은 위험도 →
```

- **A 영역**: 높은 영향, 낮은 위험 → 즉시 실행
- **B 영역**: 높은 영향, 높은 위험 → 신중한 계획 필요
- **C 영역**: 낮은 영향, 낮은 위험 → 여유 있을 때 실행
- **D 영역**: 낮은 영향, 높은 위험 → 보통 건너뜀

### 우선순위 결정 기준

1. **비즈니스 가치**
   - 사용자 영향도
   - 수익/비용 영향
   - 전략적 중요도

2. **기술적 부채**
   - 유지보수 비용
   - 버그 발생 빈도
   - 확장성 제약

3. **실행 용이성**
   - 필요 리소스
   - 기술적 복잡도
   - 팀 역량

## 🛡️ 안전한 리팩토링 프로세스

### 1. 준비 단계
```
1. 현재 상태 문서화
2. 테스트 커버리지 확보 (최소 80%)
3. 성능 기준선 측정
4. 롤백 계획 수립
```

### 2. 실행 단계
```
1. 기능 브랜치 생성
2. 작은 단위로 변경
3. 각 변경마다 테스트
4. 코드 리뷰 수행
```

### 3. 검증 단계
```
1. 자동화 테스트 실행
2. 성능 테스트 실행
3. 통합 환경 테스트
4. 사용자 수용 테스트
```

### 4. 배포 단계
```
1. 단계적 롤아웃
2. 모니터링 강화
3. 빠른 롤백 준비
4. 문서 업데이트
```

## 🚫 리팩토링 안티패턴

### 1. Big Bang 리팩토링
- **문제**: 모든 것을 한 번에 바꾸려는 시도
- **해결**: 점진적, 반복적 접근

### 2. 완벽주의
- **문제**: 100% 완벽한 코드 추구
- **해결**: 80/20 규칙 적용, 실용적 접근

### 3. 과도한 추상화
- **문제**: 미래를 위한 과도한 일반화
- **해결**: YAGNI (You Aren't Gonna Need It) 원칙

### 4. 테스트 없는 리팩토링
- **문제**: 안전망 없이 변경
- **해결**: 테스트 먼저, 리팩토링 나중

## 📏 품질 지표 및 목표

### 코드 품질 지표

| 지표 | 나쁨 | 보통 | 좋음 | 훌륭함 |
|------|------|------|------|--------|
| 순환 복잡도 | >10 | 6-10 | 3-5 | 1-2 |
| 함수 길이 (줄) | >50 | 21-50 | 11-20 | ≤10 |
| 클래스 크기 (메서드) | >20 | 11-20 | 6-10 | ≤5 |
| 중복 코드 | >10% | 5-10% | 2-5% | <2% |
| 테스트 커버리지 | <60% | 60-79% | 80-89% | ≥90% |

### 아키텍처 품질 지표

| 지표 | 설명 | 목표 |
|------|------|------|
| 모듈성 | 독립적으로 개발/배포 가능한 정도 | 높음 |
| 결합도 | 모듈 간 의존성 정도 | 낮음 |
| 응집도 | 모듈 내 요소들의 관련성 | 높음 |
| 추상화 수준 | 구현 세부사항 은닉 정도 | 적절함 |

## 🔄 지속적 개선 문화

### 1. 정기적 리팩토링
- **Boy Scout Rule**: 코드를 발견했을 때보다 깨끗하게
- **리팩토링 스프린트**: 정기적인 기술 부채 해결 시간
- **20% 규칙**: 개발 시간의 20%는 리팩토링에 할당

### 2. 팀 차원의 접근
- **코드 리뷰 문화**: 리팩토링 기회 발견
- **페어 프로그래밍**: 실시간 개선
- **지식 공유**: 리팩토링 패턴 학습

### 3. 도구 활용
- **정적 분석 도구**: 자동으로 문제 발견
- **IDE 리팩토링 기능**: 안전한 자동 리팩토링
- **CI/CD 통합**: 품질 게이트 설정
